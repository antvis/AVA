Working with data

Define data semantics

Write business definitions, model mappings, and reusable measures, with a worked sales example.

Suppose a user asks: “Show revenue by region.” Here is the order table behind that question, also used in Inspect your data:

order_idregionstatusamountrefund_amountordered_at
1Eastpaid120202026-01-03
2Eastrefunded80802026-01-04
3Eastpending20002026-01-05
4Westpaid90302026-01-06
5Eastpaid50null2026-01-07
6Westcancelled50002026-01-08

The structure tells AVA that amount and refund_amount are numbers. It does not tell AVA which orders count as revenue. You supply that meaning through semantic().

Decide what revenue means

For this example, agree on three rules:

  • Count paid and refunded orders; exclude pending and cancelled orders.
  • Subtract cumulative refunds from the original amount. A missing refund is zero. Amounts are USD.
  • Group by the order's region and use its original order date.

Apply those rules to the rows above:

OrderContribution to revenueWhy
1100 USD120 minus the 20 refund.
20 USDFully refunded: 80 minus 80.
30 USDPending, so excluded.
460 USD90 minus the 30 refund.
550 USDThe missing refund is treated as zero.
60 USDCancelled, so excluded.

East therefore has 150 USD in revenue; West has 60 USD. The definition below records the rules that produce those numbers.

Write the definition

Definitions guide query generation. They do not create database objects or enforce access rules.

Read it in three parts:

  1. description and properties explain meaning. The shared description defines revenue; model and column properties explain row grain, units, and nulls. Keys such as unit and synonyms are annotations, not special SDK options.
  2. models connects meaning to data. name: 'data' matches the discovered model. The calculated net_amount describes a per-order value. Unlisted physical columns remain available from the schema.
  3. cubes defines reusable analysis. sales groups a measure and its grouping expressions. net_revenue contains both the status filter and refund calculation. dimensions supplies region grouping; timeDimensions supplies order-date grouping.

The measure includes its eligibility rule so that it still applies when grouping by region or date. The calculated net_amount alone does not decide which orders count toward revenue.

For your own source, inspect await ava.schema() first. Match existing model and column names exactly and retain physical source qualifiers. Each semantic model requires exactly one of tableReference, refSql, or baseObject; each column requires name and type. Copy discovered types for physical fields and declare result types for calculations. See model sources for the alternatives.

You can start smaller: { description: 'Your business rules here.' } is valid. Add models for field-specific meaning, relationships for joins, and cubes for reusable measures as your questions require them.

A logical model, cube, view, or calculated column does not automatically become a queryable database object. For example, SQL using net_amount must expand its expression or define it in a subquery or CTE. The query above embeds the measure expression and reads the physical data table.

Check and maintain your definition

Before using a definition for real questions:

  1. Confirm row grain, units, eligible records, null handling, and time meaning with the data owner. For joins, check that a row is not counted multiple times.
  2. Test expressions on a small dataset with known answers, including edge cases such as the refunds and excluded orders shown above.
  3. Inspect generated SQL and compare executed results with those known answers. Setter validation checks the object structure; it does not prove the SQL or business logic is correct.

Keep the complete definition in application code or a JSON file and version it with the data contract.

i

Each setter replaces the complete definition. Loading another source or calling dispose() clears it; reapply it after loading a source. Schema and profile updates retain it.

For exact field shapes, source mappings, relationships, views, merge rules, and validation errors, continue to the semantic fields in the API reference. See Inspect your data for the other inputs and AVA API for the method signature.
