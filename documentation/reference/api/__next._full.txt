## Initialization

### Constructor

`new AVA(config: AVAConfig)`

| Parameter       | Type           | Required | Default / behavior                                            |
| --------------- | -------------- | -------- | ------------------------------------------------------------- |
| `config`        | `AVAConfig`    | Yes      | Configuration object.                                         |
| `config.llm`    | `LLMConfig`    | Yes      | [Model fields below](#model-options).                         |
| `config.engine` | `EngineConfig` | No       | `{ type: 'duckdb' }`; [engine fields below](#engine-options). |

The constructor does not load data. Engine creation happens on `source()`.

#### Model options

Fields below belong to `config.llm`.

| Field          | Type                                  | Required | Meaning / default                                                                 |
| -------------- | ------------------------------------- | -------- | --------------------------------------------------------------------------------- |
| `provider`     | `'openai' \| 'gateway'`               | No       | Defaults to OpenAI-compatible Chat Completions. Gateway reads AI_GATEWAY_API_KEY. |
| `model`        | `string \| LanguageModel`             | Yes      | Model name or a preconfigured AI SDK model instance.                              |
| `apiKey`       | `string`                              | No       | API key for the LLM provider                                                      |
| `baseURL`      | `string`                              | No       | Optional API base URL                                                             |
| `maxRetries`   | `number`                              | No       | Maximum retries for retryable model API failures. Default 3.                      |
| `onQueryUsage` | `(usage: LanguageModelUsage) => void` | No       | Optional callback for SQL-generation token usage                                  |

String model names use OpenAI-compatible **Chat Completions** by default. A supplied model object is used directly. Usage callbacks are not a complete accounting stream for every LLM request.

#### Engine options

`config.engine.type` is required when `engine` is supplied. Supported values are `duckdb`, `python`, `javascript`, `supabase`, and `clickhouse`, plus names registered through `registerEngine()`. Omitting `engine` selects DuckDB. JavaScript, Supabase, and ClickHouse accept no additional engine fields; connection credentials belong to `source()`.

##### DuckDB

Set `engine.type` to `duckdb`. These are all additional fields accepted on `engine`.

| Field                      | Type      | Required | Meaning / default                                                               |
| -------------------------- | --------- | -------- | ------------------------------------------------------------------------------- |
| `memoryLimit`              | `string`  | No       | Memory limit, e.g. '512MB'. Default '512MB'.                                    |
| `threads`                  | `number`  | No       | Number of worker threads. Default 1.                                            |
| `maxTempDirectorySize`     | `string`  | No       | Max size of the spill (temp) directory, e.g. '1GB'. Unset = unlimited.          |
| `queryTimeoutMs`           | `number`  | No       | Per-query timeout in milliseconds. Default 30000.                               |
| `allowCommunityExtensions` | `boolean` | No       | Allow DuckDB community extensions during source loading when explicitly needed. |

##### Python

Set `engine.type` to `python`. These are all additional fields accepted on `engine`.

| Field            | Type                                         | Required | Meaning / default                                                                                                                                                                                                                                                                         |
| ---------------- | -------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `execute`        | `(code: string) => Promise<ExecutionResult>` | No       | Override local python3 execution with a custom environment. Local execution is not sandboxed. Run the complete Python script and return its JSON output as ExecutionResult. Source loading and result limits are included in the script; configure remote execution deadlines separately. |
| `queryTimeoutMs` | `number`                                     | No       | Client wait limit and local process execution deadline. Default 30000 ms.                                                                                                                                                                                                                 |

##### Registered engines

Set `engine.type` to the name passed to `registerEngine()`. Additional fields are forwarded to the engine constructor as `options`. This is an SDK-only capability; the CLI supports built-in engine names.

| Field        | Type            | Required          | Meaning / default                          |
| ------------ | --------------- | ----------------- | ------------------------------------------ |
| `type`       | `string`        | Yes               | Registered engine name, such as `'sales'`. |
| Other fields | Engine-specific | Depends on engine | Validated by the registered engine.        |

## Data

### source

```typescript
source(config: DataSourceConfig): Promise<void>
```

Loads a data source through the engine. It returns no value and does not discover the schema.

```typescript
await ava.source({ type: 'json', options: { data: [{ revenue: 120 }] } });
```

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `config` | `DataSourceConfig` | Yes | Data source to load. |
| `config.type` | `SourceType` | Yes | [Source type](/documentation/data/sources/#connect-a-source), such as `json` or `csv-file`. |
| `config.options` | Source-specific object | Yes | [Reader or connection settings](/documentation/data/sources/#connect-a-source) for that type. |

Loading a source disposes the previous engine and clears the saved schema, profile, and semantic definitions. A failed load leaves no active source. Await pending operations before replacing a source.

### schema

```typescript
schema(options?: SchemaOptions, setter?: (options: SchemaOptions) => Schema): Promise<Schema>
```

Returns the structure of the loaded source. Without a setter, AVA returns the saved schema or discovers it through the engine and saves it.

```typescript
const schema = await ava.schema();
```

To supply an existing schema, pass a function that returns it:

```typescript
await ava.schema(undefined, () => savedSchema);
```

| Parameter | Type | Required | Meaning / default |
| --- | --- | --- | --- |
| `options` | `SchemaOptions` | No | `{}`; currently has no configurable fields. |
| `setter` | `(options: SchemaOptions) => Schema` | No | Returns the schema to save instead of discovering it through the engine. |

A setter receives the options object (default `{}`) and returns a `Schema` synchronously. Its result replaces the saved schema and clears the saved profile. AVA validates and copies the result; invalid results or thrown errors reject the call without changing previous metadata.

Requires a loaded source. Analysis and profiling obtain the schema when needed; direct `query()` does not. For the walkthrough, see [Inspect your data](/documentation/data/schema/).

#### Schema structure

| Field | Meaning |
| --- | --- |
| `models` | Tables or views available for queries; required. |
| `models[].name` | Model name. |
| `models[].tableReference` | Physical source identity: `table`, with optional `catalog` and `schema`. |
| `models[].columns` | Columns, each with `name`, `type`, and optional `notNull`. |
| `models[].primaryKey` | One column name, or a nonempty ordered array for a composite key. |
| `models[].uniqueKeys` | Array of alternative keys; each entry is a column name or a composite-key array. |
| `relationships` | Discovered foreign-key relationships, when available. |
| `views` | Named view queries with `name` and `statement`, when available. |

The details depend on the source and engine. A query result's `schema` describes its output columns and is not a source `Schema`.

### profile

```typescript
profile(options?: ProfileOptions, setter?: (options: ProfileOptions) => Profile): Promise<Profile>
```

Calculates and saves statistics for the loaded source through the engine. Each call without a setter computes a fresh profile and requires engine profiling support.

```typescript
const profile = await ava.profile({ metrics: ['row_count', 'mean'] });
```

To supply an existing profile, pass a function that returns it:

```typescript
await ava.profile(undefined, () => savedProfile);
```

| Parameter | Type | Required | Meaning / default |
| --- | --- | --- | --- |
| `options` | `ProfileOptions` | No | `{}`; uses the default metrics below. |
| `options.metrics` | `MetricConfig[]` | No | Metrics for engine computation. A supplied list replaces the defaults. |
| `setter` | `(options: ProfileOptions) => Profile` | No | Returns the profile to save instead of computing it through the engine. |

A setter receives the options object (default `{}`) and returns a `Profile` synchronously. It does not require engine profiling support. AVA validates and copies its result; invalid results or thrown errors reject the call without changing previous metadata. The options are passed to the setter; AVA does not calculate or filter metrics on its behalf.

Requires a loaded source. Both paths replace the saved profile, which analysis, translation, and suggestions can reuse. Setting a profile does not replace the saved schema.

#### Profile format

A profile attaches observations to existing schema models and columns by name:

| Field | Meaning |
| --- | --- |
| `models[].name` | Model to enrich. |
| `models[].metrics` | Table statistics such as `row_count`. |
| `models[].columns[].name` | Column to enrich within that model. |
| `models[].columns[].metrics` | Column statistics such as `mean`. |
| `models[].columns[].properties.logicalType` | Normalized category: `numeric`, `string`, `boolean`, `date`, or `unknown`. |

A missing metric means it was not computed, not zero. Setting a schema clears the saved profile, so supply the schema first when providing both manually. Loading another source or calling `dispose()` clears schema, profile, and semantic definitions. Updating schema or profile retains semantic definitions.

#### Metrics

The default metrics are `row_count`, `null_count`, `distinct_count`, `top_values`, `min`, `max`, and `mean`. Additional built-in metrics are `duplicate_count`, `min_length`, `max_length`, `sum`, `stddev`, and `median`.

Each entry is a metric name or an object with an `id` and metric-specific options:

```typescript
await ava.profile({
  metrics: ['row_count', { id: 'top_values', limit: 5 }],
});
```

| Field | Type | Default / behavior |
| --- | --- | --- |
| `id` | `string` | Required for object entries; the metric name. |
| `limit` | `number` | `top_values` only. Default `3`; a non-negative safe integer. |
| `maxDistinctRatio` | `number` | `top_values` only. Default `0.5`; a finite number from `0` to `1`. |

Other built-in metrics accept no additional options. Unknown metrics and unknown option names are rejected when the engine computes the profile. Availability depends on the engine and field type.

`metrics: []` produces empty metric objects. A new profile replaces previous statistics; metrics are not accumulated.

### semantic

```typescript
semantic(options?: SemanticOptions, setter?: (options: SemanticOptions) => Semantic): Promise<Semantic>
```

Reads or replaces the semantic definitions for the loaded source. Without a setter, returns the saved definitions, initially `{}`. This call does not discover the schema, compute a profile, or call an LLM.

```typescript
await ava.semantic(undefined, () => ({
  description: 'Sales reporting; amounts are in USD.',
  cubes: [{
    name: 'revenue',
    baseObject: 'data',
    measures: [{ name: 'total', expression: 'SUM(revenue)', type: 'DOUBLE' }],
  }],
}));

const definitions = await ava.semantic();
await ava.semantic(undefined, () => ({})); // Clear the saved definitions.
```

| Parameter | Type | Required | Meaning / default |
| --- | --- | --- | --- |
| `options` | `SemanticOptions` | No | `{}`; currently has no configurable fields. |
| `setter` | `(options: SemanticOptions) => Semantic` | No | Returns the semantic definitions to save, replacing the previous definitions. |

The setter receives the options object and returns a `Semantic` synchronously. AVA validates and copies the result; invalid results or thrown errors leave the previous definitions unchanged. Requires a loaded source. Source replacement and disposal clear these definitions; schema and profile updates retain them.

`Semantic` contains business definitions and excludes model and column `metrics`; supply statistical observations through `profile()`. The combined context passed to engines remains a `DataModel`.

Start with [Define data semantics](/documentation/data/semantic/) for the authoring walkthrough and sales example. See [semantic fields](#semantic-fields) for the detailed reference.

For `analyze()`, `translate()`, and `suggest()`, AVA merges models and columns by name with the schema and profile. Unspecified models, columns, and observations remain available; model and column properties merge by key, with semantic values taking precedence. A supplied relationship or view list replaces its discovered counterpart, including when the list is empty. Each semantic model must declare exactly one source: `tableReference`, `refSql`, or `baseObject`.

These definitions provide context for query generation. Declaring a cube, view, or calculated column does not create database objects; generated queries must work with the configured engine.

## Analysis and queries

### analyze

`analyze(query: string, config?: AnalysisConfig): Promise<AnalysisResponse>`

| Parameter                    | Type                               | Required                  | Default / behavior                                                                                                              |
| ---------------------------- | ---------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `query`                      | `string`                           | Yes                       | Natural-language question.                                                                                                      |
| `config`                     | `AnalysisConfig`                   | No                        | `{}`.                                                                                                                           |
| `config.includeSummary`      | `boolean`                          | No                        | `true`; `false` returns empty `text`.                                                                                           |
| `config.maxRows`             | `number`                           | No                        | `200`; see [execution limits](#executionoptions).                                                                               |
| `config.maxResultBytes`      | `number`                           | No                        | `1048576`; see [execution limits](#executionoptions).                                                                           |
| `config.strategy`            | `AnalysisStrategyConfig`           | No                        | Direct analysis.                                                                                                                |
| `config.strategy.type`       | `'direct'` / `'loop'` | When strategy is provided | Selects the strategy.                                                                                                           |
| `config.strategy.maxRetries` | `number`                           | No; `direct` only         | `2` with explicit `type: 'direct'`; currently `10` when the strategy is omitted. Correction attempts after the first execution. |
| `config.strategy.maxSteps`   | `number`                           | No; `loop` only           | `12`; maximum reasoning steps.                                                                                                  |

These retry controls differ from `llm.maxRetries`. See [strategy behavior and requirements](/documentation/analysis/strategies/).

Requires a loaded source. Returns an [ExecutionResult](#executionresult) plus:

| Result field | Type     | Presence | Meaning                                                                   |
| ------------ | -------- | -------- | ------------------------------------------------------------------------- |
| `query`      | `string` | Always   | Original question.                                                        |
| `text`       | `string` | Always   | Summary, or empty when disabled.                                          |
| `markdown`   | `string` | Optional | Markdown content.                                                         |
| `sql`        | `string` | Optional | Executed query or DSL; the property name is retained for non-SQL engines. |

### translate

`translate(query: string): Promise<string>`

| Parameter | Type     | Required | Meaning                    |
| --------- | -------- | -------- | -------------------------- |
| `query`   | `string` | Yes      | Natural-language question. |

Requires a loaded source. Returns generated DSL without executing it; use `query()` to execute that string.

### query

`query(dsl: string, options?: ExecutionOptions): Promise<ExecutionResult>`

| Parameter                | Type               | Required | Default / behavior                                      |
| ------------------------ | ------------------ | -------- | ------------------------------------------------------- |
| `dsl`                    | `string`           | Yes      | Executable statement in the selected engine's language. |
| `options`                | `ExecutionOptions` | No       | Default execution limits below.                         |
| `options.maxRows`        | `number`           | No       | `200`.                                                  |
| `options.maxResultBytes` | `number`           | No       | `1048576` bytes.                                        |

Requires a loaded source. Does not generate or summarize a query with the model.

#### ExecutionOptions

| Field            | Type     | Default           | Accepted values / behavior                                                                                       |
| ---------------- | -------- | ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `maxRows`        | `number` | `200`             | Rounded down and bounded to `1`–`1000000`; values outside the safe integer range after rounding use the default. |
| `maxResultBytes` | `number` | `1048576` (1 MiB) | Finite values are rounded down and clamped to at least `1`; non-finite values use the default.                   |

These limits bound returned data; they are separate from engine execution timeouts.

#### ExecutionResult

| Field           | Type                             | Presence       | Meaning                                                 |
| --------------- | -------------------------------- | -------------- | ------------------------------------------------------- |
| `schema`        | `QueryColumn[]`                  | Always         | Returned column metadata.                               |
| `schema[].name` | `string`                         | Always         | Column name.                                            |
| `schema[].type` | `string`                         | Optional       | Native type name, if available.                         |
| `data`          | `T[]`                            | Always         | Returned rows.                                          |
| `truncated`     | `true`                           | When truncated | Result was bounded.                                     |
| `truncatedBy`   | `'maxRows'` / `'maxResultBytes'` | When truncated | Limit that stopped the result.                          |
| `rowCount`      | `number`                         | When known     | Row count when execution reaches the end of the result. |

### suggest

`suggest(count?: number): Promise<SuggestResult[]>`

| Parameter | Type     | Required | Default / behavior                  |
| --------- | -------- | -------- | ----------------------------------- |
| `count`   | `number` | No       | `3`; requested number of questions. |

Requires a loaded source. Returns suggestions sorted by descending score, each with `query: string`, `score: number` (0–1), and `reason: string`.

Exported by both SDK entry points. Register an engine implemented in your own application before loading a source.

### executionResult helper

`executionResult<T>(rows: T[], schema: QueryColumn[], options?: ExecutionOptions, upstreamTruncatedBy?: 'maxRows' | 'maxResultBytes'): ExecutionResult<T>`

A synchronous helper exported by both SDK entry points for custom engine implementations. Import it from `@antv/ava` or `@antv/ava/browser`.

| Parameter             | Type                              | Required | Meaning / default                                                                                    |
| --------------------- | --------------------------------- | -------- | ---------------------------------------------------------------------------------------------------- |
| `rows`                | `T[]`                             | Yes      | Rows produced by the engine.                                                                         |
| `schema`              | `QueryColumn[]`                   | Yes      | Output columns; each has `name: string` and optional `type: string`.                                 |
| `options`             | `ExecutionOptions`                | No       | `{}`; uses the [execution limits](#executionoptions) above.                                          |

## Semantic model reference

### Semantic fields

All six top-level fields are optional. Supply only the sections your application needs. Names and required expressions must be nonempty strings. `properties` contains JSON values with finite numbers; keys such as `description`, `unit`, `synonyms`, and `owner` are application conventions, not built-in SDK behaviors.

| Field | Shape | Purpose |
| --- | --- | --- |
| `description` | `string` | Shared business context, terminology, eligibility, and time conventions. |
| `properties` | `Record<string, JsonValue>` | Shared annotations. |
| `models` | Model definitions below | Physical and logical datasets, column meanings, and source mappings. |
| `relationships` | Relationship definitions below | Joins between named models. |
| `views` | View definitions below | Reusable named SQL queries. |
| `cubes` | Cube definitions below | Measures, grouping expressions, and drill-down paths. |

### Semantic models

| Field | Required | Meaning |
| --- | --- | --- |
| `name` | Yes | Logical model name; matches a schema model by name or adds a new one. |
| `tableReference` | One source selector | `{ table, schema?, catalog? }`; physical identifiers, independent of the logical name. Extra source attributes must be JSON values. |
| `refSql` | One source selector | SQL defining the source rows before column mappings and calculations. |
| `baseObject` | One source selector | Name of another model or view supplying the rows. |
| `columns` | No | Column definitions below; unlisted existing columns are retained. |
| `primaryKey` | No | One column name or a nonempty ordered array for a composite key. |
| `uniqueKeys` | No | Array of keys, each a column name or a nonempty composite-key array. |
| `dialect` | No | SQL dialect for `refSql`; otherwise use the execution context. |
| `properties` | No | Model annotations, especially row grain and business purpose. |

A primary or unique key is a declaration, not an observed statistic. Verify it against the source. `primaryKey: ['tenant_id', 'order_id']` is one composite key. `uniqueKeys: ['email', ['tenant_id', 'external_id']]` declares two alternative unique keys.

### Semantic columns

| Field | Required | Meaning |
| --- | --- | --- |
| `name` | Yes | Name within the owning model; used to match existing columns. |
| `type` | Yes | Declared type, or target model name for a relationship column. |
| `properties` | No | Column context such as description, units, enum meanings, or null conventions. |
| `expression` | No | SQL mapping or calculation over the source; `null` or omission supplies none. |
| `isCalculated` | No | Boolean marking a derived column; does not compute it. |
| `isPrimaryKey` | No | Boolean marking membership in the declared primary key. |
| `notNull` | No | Declared non-null constraint; omission is unspecified. |
| `relationship` | No | Relationship identifier for navigation, not a foreign-key column name. |

### Semantic relationships and views

| Field | Required | Meaning |
| --- | --- | --- |
| `relationships[].name` | Yes | Identifier, also used by column navigation. |
| `relationships[].models` | Yes | Exactly two model names, ordered first to second. |
| `relationships[].joinType` | Yes | `ONE_TO_ONE`, `ONE_TO_MANY`, `MANY_TO_ONE`, or `MANY_TO_MANY`. |
| `relationships[].condition` | Yes | SQL join predicate with qualified columns. |
| `relationships[].properties` | No | Business context for the relationship. |
| `views[].name` | Yes | Logical name for the query. |
| `views[].statement` | Yes | SQL defining the result; saving it does not execute it. |
| `views[].dialect` | No | SQL dialect; otherwise use the execution context. |
| `views[].properties` | No | Purpose and business conventions. |

Relationships and views accept additional JSON-valued attributes whose meaning is agreed on by your application and consumers.

### Semantic cubes and expressions

| Field | Required | Meaning |
| --- | --- | --- |
| `name` | Yes | Cube identifier. |
| `baseObject` | Yes | Model or view supplying rows to aggregate. |
| `measures` | Yes | Nonempty array of aggregation definitions. |
| `dimensions` | No | Grouping definitions. |
| `timeDimensions` | No | Date/time grouping definitions; granularity is chosen at query time. |
| `hierarchies` | No | Map of names to nonempty dimension-name arrays, ordered coarsest to finest. |
| `properties` | No | Cube annotations. |

Each entry in `measures`, `dimensions`, and `timeDimensions` uses the same fields:

| Field | Required | Meaning |
| --- | --- | --- |
| `name` | Yes | Expression identifier within the cube. |
| `expression` | Yes | SQL aggregation for a measure, grouping expression for a dimension. |
| `type` | Yes | Declared result type. |
| `description` | No | Business meaning of the expression. |
| `properties` | No | Annotations such as units or synonyms. |

For a calendar drill-down, define dimension expressions for `year`, `month`, and `order_date`, then declare `hierarchies: { calendar: ['year', 'month', 'order_date'] }`. A hierarchy describes a path; it does not generate those fields.

Model, column, cube, and expression objects reject unknown fields; put application annotations in `properties` where supported.

### Semantic model sources

Call `schema()` and inspect model names, source references, and column types before writing mappings. Names match exactly within their owning model. The inline JSON source in the sales example is exposed as `data`; other sources can have different names and catalog or schema qualifiers.

Every entry in `models` needs a `name` and **exactly one** source selector, even when you only want to add a description to an existing model:

| Selector | Use it when | Example |
| --- | --- | --- |
| `tableReference` | The model maps to a physical table or database view. Retain the discovered qualifiers. | `{ tableReference: { schema: 'public', table: 'orders' } }` |
| `refSql` | SQL defines the source rows of a logical model. | `{ refSql: "SELECT * FROM orders WHERE status = 'paid'" }` |
| `baseObject` | Another model or declared view supplies the source rows. | `{ baseObject: 'paid_orders' }` |

Use the existing schema model's `name` to enrich it. A different name adds a logical model; it does not rename the underlying table. A column needs both `name` and `type`, including when adding only a description. Copy the discovered type for physical columns; specify the result type for calculations.

`baseObject`, `refSql`, and column `expression` describe mappings for the query generator. A logical name is not automatically executable in `query()`. For example, a query using a calculated `net_amount` must inline its expression or define it in a subquery or CTE.

### Semantic join and view examples

Add relationships when analysis spans more than one model. Add views when a reusable SQL definition makes business logic clearer. These snippets assume an existing source exposing `orders` and `customers`; they are separate from the single-table sales example.

#### Relationship example

```typescript
import type { Semantic } from '@antv/ava';

const semantic = {
  relationships: [{
    name: 'order_customer',
    models: ['orders', 'customers'],
    joinType: 'MANY_TO_ONE',
    condition: 'orders.customer_id = customers.id',
    properties: { description: 'Each order belongs to one customer.' },
  }],
} satisfies Semantic;
```

`models` is an ordered pair. `MANY_TO_ONE` means many rows in the first model can match one row in the second. `joinType` describes cardinality; it does not choose `LEFT JOIN` or `INNER JOIN`. The join condition must include all parts of a composite key.

If you expose a relationship navigation column, set its `relationship` to the relationship's **name**, and its `type` to the target model name, for example `{ name: 'customer', type: 'customers', relationship: 'order_customer' }`. The physical foreign-key column remains `customer_id`.

Check grain before aggregating across a join. Joining one order to many line items can repeat the order amount. A cardinality declaration supplies context; AVA does not verify uniqueness or automatically prevent double counting.

#### View and derived model example

```typescript
import type { Semantic } from '@antv/ava';

const semantic = {
  views: [{
    name: 'paid_orders',
    statement: "SELECT * FROM orders WHERE status = 'paid'",
    dialect: 'duckdb',
    properties: { description: 'Paid orders only; this excludes fully refunded orders.' },
  }],
  models: [{
    name: 'paid_sales',
    baseObject: 'paid_orders',
    properties: { description: 'One row per paid order.' },
  }],
} satisfies Semantic;
```

Here a logical model references a named query. A generator can expand that query as a CTE or subquery. `await ava.query('SELECT * FROM paid_orders')` only works if that name already exists in the execution engine; saving this definition does not create it. A model's `refSql` can describe its source query directly when a separate named view is unnecessary.

### Save and combine semantic definitions

Keep one complete definition in your application, version it alongside the source it describes, and pass it to AVA after `source()`. Calling the setter replaces the saved semantic object. It does not append definitions or patch the previous object.

```typescript
await ava.semantic(undefined, () => completeDefinitions);
const saved = await ava.semantic();
await ava.semantic(undefined, () => ({})); // Clear all saved semantics.
```

Definitions can live in code or in an application-owned JSON file. For example, after loading a source in Node.js:

```javascript
const { readFile } = require('node:fs/promises');
const definitions = JSON.parse(await readFile('./sales-semantic.json', 'utf8'));
await ava.semantic(undefined, () => definitions);
```

The JSON file contains the definition object, without the JavaScript variable declaration or setter. AVA accepts an object, not a file path; if you store YAML, parse it in your application before calling the setter. Reading and parsing the file can happen asynchronously before the setter returns the object.

When an operation needs its data model, AVA combines the inputs in this order:

| Combination | Behavior |
| --- | --- |
| Schema, then profile | Observations attach to existing models and columns by name. |
| Semantic models | Matching names enrich the model; new names add logical models. A supplied source selector takes precedence. |
| Semantic columns | Matching names enrich columns; new names add columns. Unlisted models, columns, and profile metrics remain available. An empty column list does not remove discovered columns. |
| Model and column `properties` | Merge by key; semantic values win for matching keys. Nested JSON values are replaced as values, not recursively merged. |
| Other supplied model and column fields | Semantic values replace corresponding fields, including types and key declarations. |
| Top-level fields | Supplied values replace their counterparts. In particular, relationship and view arrays are replaced as complete lists; `[]` clears that list in the combined context. |

Omitting a section retains the corresponding schema context. If adding a relationship alongside discovered foreign keys, include the discovered relationships you want to keep in the supplied list. Reading `schema()`, `profile()`, or `semantic()` still returns that input, not the combined model; there is no public method to read the merged `DataModel`.

Changing the schema clears the saved profile and retains semantic definitions. Profiling replaces observations and retains semantic definitions. Loading another source or calling `dispose()` clears all three. Reapply your saved definition after loading a new source, and review mappings if its structure changed. Calls require a loaded source; a failed source replacement leaves no active source.

The setter validates and copies its returned object. A validation failure or thrown error leaves the previous semantic definition in place. A setter emits `semanticstart` and `semanticend`; a plain read emits neither. See [Events](/documentation/reference/events/).

### Semantic validation

Structural validation checks field shapes, required fields, source-selector exclusivity, and nonempty measure lists. It does **not** prove that SQL is valid, referenced objects exist, key declarations hold, units are consistent, or business rules are correct. Duplicate semantic model names and duplicate column names within a model are rejected when building the combined model for analysis, translation, or suggestions, rather than by the setter alone.

Use the sales example’s pattern for your own definition:

1. Inspect `schema()` and map exact names and physical types. For remote sources, preserve catalog and schema qualifiers.
2. Have the business owner review grain, eligible statuses, null handling, units, and time meaning.
3. Run each declared expression against a small fixture with known answers. Include excluded rows, nulls, refunds, and join duplication where relevant.
4. Inspect `translate()` output for those same questions, then compare executed results with the known answers. A successful setter is not a successful end-to-end check.
5. Repeat the checks when the source schema or business definitions change.

| Symptom | What to check |
| --- | --- |
| Setter rejects a model | Include exactly one of `tableReference`, `refSql`, or `baseObject`; columns need `name` and `type`. |
| Setter rejects a cube | Include `baseObject` and at least one measure with `name`, `expression`, and `type`. |
| Setter rejects statistics | Put model and column `metrics` in `profile()`, not `semantic()`. |
| Query says a logical name does not exist | Check whether the SQL expands its declared expression, view, or model into executable SQL. |
| A discovered join disappears | Your relationship list replaced the discovered list. Include all joins you still need. |
| Numbers are inflated | Check row grain, join cardinality, duplicate keys, eligibility filters, and refund treatment. |
| A rule is ignored | Inspect the generated query. Enforce mandatory access rules in the data or execution layer. |
