AVA 产品介绍演示脚本
建议总时长 10 分钟

四段分别回答：能帮我快速做什么、怎样理解我的业务、能否继续深入分析、如何进入我的产品。
所有数据均为模拟或合成数据，不是真实客户案例。下列数值是实际数据的参考结果，不是预先编写给 Agent 的回答。

一、演示前准备

1. 当前包的 live-inputs 只放数据与业务定义。把该目录单独复制到一个干净演示目录，在那个目录开启已加载 AVA Skill 的 Agent。不要把整个素材包放进演示 Agent 的工作区，避免读到参考答案或参考 SQL。
2. 本文提示词中的 ./01-sales、./02-semantics、./03-retention，均相对于这个干净目录。将新生成的结果保存在 ./demo-output 中。
3. 提前确认 Node.js、AVA CLI、Agent Skill、数据加载和图表渲染可用。用 AVA Skill 时由 Agent 推理、写查询和解释，AVA 连接数据、执行查询、渲染图表，不另需 AVA 模型密钥。
4. SDK 自行调用 analyze、visualize 的路径需要配置模型。演示中不要把它与 Agent Skill 路径混成同一条调用链。
5. 参考结果、已生成图表及 SQL 在各场景目录，完整参考答案在 reference-answers.json，校验说明在 validation.json。正式演示只给 Agent 数据和语义。
6. 图表 HTML 需要联网加载 GPT-Vis。五份 HTML 已生成，目前未完成浏览器视觉验收。正式录制前逐一打开，确认图表、单位和标签可读，并准备已核验结果表作为备用。
7. 本次已执行参考 SQL、验证金额/去重/队列口径及主要数值。没有执行完整 Agent 多轮彩排，也没有实现或运行场景四的业务产品界面及 SDK 集成。

二、场景一：拿到一份表，快速看懂变化
时长 1 分 30 秒
角色 销售运营
核心价值 从文件到可讨论的结论

数据准备
使用 ./01-sales/sales.csv，8 行数据，4 个产品、2 个月。
字段 month（月份）、product（产品）、revenue（已确认收入，美元）。每行是一款产品在一个月的收入汇总，不是订单明细。没有成本、渠道或流量字段。
本场景有意使用小而完整的数据，观众能直接核对计算过程。此数据无缺失值，不演示清洗收益。

00:00 至 00:15 开场
画面：打开 CSV，短暂展示三个字段和八行数据。
口播：“这是我刚收到的产品收入表。我想知道这个月整体怎么样，以及变化主要来自哪里。”

00:15 至 00:55 第一轮用户提问
“请用 AVA Skill 分析 ./01-sales/sales.csv。先确认字段和行粒度，再比较2025年1月与2月的收入，按产品拆解增减，找出主要贡献。金额单位是美元。把各产品收入变化画成水平条形图，结论、结果表、实际执行的SQL和图表保存到 ./demo-output/01-sales。”
操作：发送提示词；简短展示加载和字段检查；聚焦整体结果与产品变化图。
后台参考：ava source → ava schema → ava query → ava viz。由 Agent 编写查询与图表配置。建议问题若要展示，作为单独的可选步骤，由 Agent 根据字段提出，不强制调用需要模型配置的 ava suggest。

00:55 至 01:15 第二轮用户提问
“Analytics贡献了多少净增量？有没有产品在抵消增长？核对产品变化之和是否等于整体变化。”
操作：让 Agent 基于已有会话和结果补充贡献占比及抵消项。

最后展示的结果

Analytics     12000     18000      +6000

主画面：30000 → 37500，+25%；下方展示四条产品增减条形；底部提供查询和结果。

三、场景二：同一份订单，为什么两个部门得出相反结论
时长 3 分钟
角色 财务负责人、交易运营负责人
核心价值 业务定义参与分析

数据准备
使用 ./02-semantics/sales.csv，18971条订单明细、15510笔订单。
准备 semantic-finance.json 与 semantic-trading.json 两份定义。两份定义不含异常地点或结论。
关键字段：order_id、line_id、status、order_kind、paid_at、completed_at、line_paid_amount、refund_amount、commission_rate、selling_store_name、channel、product_name。
财务：已履约外部客户订单；按履约月；代销计佣金；金额与退款分别逐行四舍五入到分。
交易：已支付/已发货/已履约外部客户订单；按支付月；代销计全额；包含已支付未履约订单。
共同规则：退款快照截至2026-10-05，回记原报表月份；订单明细不能当订单数，order_paid_amount重复出现在多行，不能直接累加；销售归因用selling_*，不用fulfillment_*。

00:00 至 00:20 开场
画面：同一数据文件旁放两张报表标题，“财务经营月报”和“交易运营月报”。此时不提前展示答案。
口播：“两个团队都问9月净销售额怎么变了，但他们说的净销售额，业务含义不同。”

00:20 至 01:15 第一轮用户提问
“请用AVA Skill加载 ./02-semantics/sales.csv，并读取、加载 ./02-semantics/semantic-finance.json。严格按其中的财务经营口径，比较2026年9月与8月净销售额，说明变化金额、比例及主要来源。按销售责任门店、渠道、商品组合拆解，保留增长抵消项。展示采用的口径、实际查询、结果和图表，保存到 ./demo-output/02-finance。”
操作：展示一眼口径卡；加载语义；执行总额及贡献查询；呈现财务结果。
口径卡重点显示：履约月、佣金、已履约。
后台：先读schema；加载完整semantic JSON；生成查询时显式采用定义。semantic不会自动改写Agent手写SQL，也不是访问控制规则。

01:15 至 02:10 第二轮用户提问
“同一份订单数据，改用 ./02-semantics/semantic-trading.json 的交易运营口径，重新回答同一个问题。把两种口径的结果并排，并列出影响结果的定义差异。结果另存到 ./demo-output/02-trading，保留上一轮证据。”
操作：替换完整语义；重新执行查询；并排展示两张口径卡和两组结果。
演示时也可提前建立独立的财务、交易会话，保证两侧结果不会互相覆盖。

02:10 至 02:45 第三轮用户提问
“为什么一个下降、一个增长？请解释时间归属、计入范围和代销确认方式的差异。没有逐因素计算时，不要给每条规则编造贡献金额。”
操作：突出三条业务差异；打开各口径对应的SQL片段和结果表，不滚动整份长SQL。

财务：8月4293025.42，9月3697575.18，减少595450.24，下降13.87%。
主要下降组合：深圳南山店／线上商城／电动升降桌，减少558776.37元。
广州天河店总额增加66713.31元，抵消部分下降。

“字段告诉我们数据长什么样，业务定义告诉我们这道题该怎么算。AVA可以把这些定义带进分析，并保留计算依据。”
不要声称本场景证明了准确率提升，也不要刻意让无语义的一侧给错答案。若演示无语义提问，合理追问口径本身就是有效行为。

四、场景三：新增翻倍，活跃为什么没有同步增长
时长 3 分钟
角色 产品增长负责人
核心价值 连续追问，逐步缩小排查范围

数据准备
使用 ./03-retention/retention.sqlite，包含 users（7300人）和 events（33880条事件）。同目录semantic.json定义指标。
users字段：user_id、registered_at、channel。每个用户一行，含300名历史用户。
events字段：user_id、event_date、event_name。按用户、日期、事件去重；core_action为本演示的活跃行为。
前期：2026-07-01至07-14；近期：2026-07-22至08-04，均为14天且含首尾日。
事件快照截至08-11，近期最后一批注册用户也已观察完整D7。时间按Asia/Shanghai自然日。
DAU包含历史用户及新用户，日均DAU为每天去重人数的平均值。D7留存是注册后第7个自然日当天活跃，不能改成“7天内有活跃”。

00:00 至 00:15 开场
画面：只显示业务问题，不提前给出渠道答案。
口播：“新增人数翻倍，活跃增长却没有跟上。我想知道该从哪里排查。”

00:15 至 00:55 第一轮用户提问
“请用AVA Skill分析 ./03-retention/retention.sqlite，读取并加载 ./03-retention/semantic.json。比较2026年7月1日至14日与7月22日至8月4日的新增用户和日均DAU，新增与活跃的增长是否同步？保留两个时间段、单位与计算口径。把结果保存到 ./demo-output/03-retention。”
操作：查看两张表及连接字段；分别算注册人数和日均DAU，不直接用连接后行数计人数。
展示：新增1400→2800，+100%；日均DAU580→740，+27.59%。

00:55 至 01:35 第二轮用户提问
“这两批新用户注册后的留存表现有什么不同？请比较D1、D3、D7，先确认观察窗口完整，再画图。”
操作：按注册队列连接事件；未回访者仍保留在分母；以用户去重；绘制指定日留存折线。
展示：D1为70%→50%，D3为60%→40%，D7为50%→30%，下降20个百分点。
补充人数：D7回访700→840，只增加20%。

01:35 至 02:15 第三轮用户提问
“按注册渠道拆开看。是每个渠道自身的D7留存下降，还是新增用户的渠道结构变了？给我各渠道新增人数、占比和D7留存。”
操作：在已有队列范围按渠道拆分；同时展示人数与比例，不能平均渠道留存率。
展示结果：
自然渠道：新增1120→1120，占比80%→40%，D7留存60%→60%。
推广渠道：新增280→1680，占比20%→60%，D7留存10%→10%。
解释公式：前期80%×60%+20%×10%=50%；近期40%×60%+60%×10%=30%。
画面：左侧留存折线，右侧渠道新增结构表或图。

02:15 至 02:45 第四轮用户提问
“这种渠道结构变化从哪批注册用户开始？目前能得出什么结论，还需要补什么数据才能判断原因和下一步动作？”
操作：将注册队列按日细分；定位推广渠道新增在7月15日从每天20人变为120人，自然渠道仍每天80人；各渠道D7留存保持不变。

最后展示的结果
事实一：新增翻倍，日均DAU增长27.59%。
事实二：整体D7留存下降20个百分点，但两个渠道各自的D7留存没有下降。
事实三：从7月15日队列起，低留存的推广渠道新增规模扩大，改变了整体用户结构。
结论：“整体留存下降可由渠道结构变化解释；新增增长没有带来同比例的D7回访增长。当前数据尚不足以量化其对全部DAU变化的因果影响。”
后续排查：补充推广渠道的活动/投放与落地页变更记录、成本和转化数据，核查新增结构变化及是否符合获客目标。不能直接把问题归因于投放故障，或据此决定削减预算。
已生成参考图：03-retention/retention-curve.html、03-retention/channel-mix.html。

收尾口播
“从一个总量问题，逐步追问到留存、渠道和时间，分析让我们得到更具体的排查对象，也知道还缺哪些证据。”

产品演示范围固定为2026年8月至9月、财务口径、销售责任门店。判定规则固定为“按净销售额下降金额排序”，不是未经定义的健康评分。
预期产品需提供：业务口径提示、问题输入框、结果卡与图表、门店筛选/下钻、查询及结果查看入口。
这些是待接入产品的交互设计，不是本次已实现的界面。若尚无业务界面，用已生成图表加结果表排练，并明确标注“产品交互方案”。

六、演示节奏与验收

第一段让观众看到能做什么，第二段解释怎样算对业务，第三段展示能继续问多深，第四段说明如何进入产品。
每段主画面只突出一个结论，SQL与完整结果放在可展开区域。场景二以口径对照为主画面，场景三以追问后的结论变化为主画面。
不要宣称“实时数据库接入”“权限控制”“自动归因”“准确率提升”已在这套脚本中验证。
彩排通过标准：数据范围与口径正确、关键数值吻合、分项与总体勾稽、没有漏掉抵消项、D7队列观察完整、图表标注清楚、每次追问的证据能单独找回。
现场模型措辞、SQL写法或图表样式可以不同，不要求逐字复述本文。遇到等待或失败，切换到标注为预先计算的参考图表与结果，不把备用结果描述为刚刚生成。
