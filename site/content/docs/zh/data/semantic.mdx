同一句“ **按地区统计收入** ”，口径不同，结果就可能不同。以下沿用[了解数据结构](/documentation/data/schema/)中的六笔订单，看看该怎样把口径说明白：

| order_id | region | status | amount | refund_amount | ordered_at |
| --- | --- | --- | --- | --- | --- |
| 1 | East | paid | 120 | 20 | 2026-01-03 |
| 2 | East | refunded | 80 | 80 | 2026-01-04 |
| 3 | East | pending | 200 | 0 | 2026-01-05 |
| 4 | West | paid | 90 | 30 | 2026-01-06 |
| 5 | East | paid | 50 | `null` | 2026-01-07 |
| 6 | West | cancelled | 500 | 0 | 2026-01-08 |

数据结构能告诉 AVA，`amount` 和 `refund_amount` 是数值；但无法说明哪些订单该计入收入。你可以通过 `semantic()` 补充这层业务含义。

<Heading as="h2" id="decide-what-revenue-means">先明确收入的口径</Heading>

本例约定三条规则：

- 计入 `paid` 和 `refunded` 订单，排除 `pending` 和 `cancelled` 订单。
- 用原始金额减去累计退款；退款缺失时按零处理。金额单位为美元。
- 按订单所属地区分组，时间维度使用原始下单日期。

将这些规则应用到上面的数据：

| 订单 | 计入收入的金额 | 原因 |
| --- | --- | --- |
| 1 | 100 美元 | 120 减去 20 的退款。 |
| 2 | 0 美元 | 全额退款，80 减去 80。 |
| 3 | 0 美元 | 待支付，排除。 |
| 4 | 60 美元 | 90 减去 30 的退款。 |
| 5 | 50 美元 | 退款缺失，按零处理。 |
| 6 | 0 美元 | 已取消，排除。 |

因此，East 的收入为 **150 美元** ，West 为 **60 美元** 。下面的语义定义将记录产生这些结果的规则。

<Heading as="h2" id="write-the-definition">编写定义</Heading>

将模型保存为 `sales.ossie.yaml`。逻辑数据集 `orders` 指向物理表 `data`，`fields` 定义可分组字段，`metrics` 记录指标公式。数据集级指标里的 `source.amount` 指向该数据集的来源列。

```yaml
version: 0.3.0.dev0
name: sales_reporting
description: 订单与累计退款，金额单位为美元。
datasets:
  - name: orders
    source: data
    primary_key: [order_id]
    fields:
      - name: order_id
        expression: { sql: order_id }
        datatype: Integer
      - name: region
        expression: { sql: region }
        datatype: String
      - name: order_date
        expression: { sql: "CAST(ordered_at AS DATE)" }
        datatype: Date
        dimension: { is_time: true }
    metrics:
      - name: net_revenue
        description: 扣除退款后的销售收入，金额单位为美元。
        datatype: Decimal
        expression:
          sql: >-
            SUM(CASE WHEN source.status IN ('paid', 'refunded')
              THEN source.amount - COALESCE(source.refund_amount, 0)
              ELSE 0 END)
```

<Heading as="h2" id="save-the-definition-and-see-the-result">加载模型</Heading>

先加载数据源，再导入模型。CLI 接收 YAML 或 JSON 文件，也可以通过 `--file -` 从标准输入读取。

```sh
ava semantic "$DATASET_ID" --file sales.ossie.yaml
ava semantic "$DATASET_ID" > sales.ossie.json
ava semantic "$DATASET_ID" --clear
```

SDK 接收相同结构的对象。用 `parseSemantic` 解析 YAML 或 JSON 文本。

```typescript
import { readFile } from 'node:fs/promises';
import { parseSemantic } from '@antv/ava';

const model = parseSemantic(await readFile('sales.ossie.yaml', 'utf8'));
await ava.semantic(undefined, () => model);
const saved = await ava.semantic();
```

每次导入都会替换会话模型。加载新数据源或调用 `dispose()` 会清除模型。更新 schema 和 profile 会保留模型。`analyze()`、`translate()` 和 `suggest()` 会同时使用业务模型和物理元数据。调用 `query()` 时，在提交的查询中明确应用这些定义。

<Heading as="h3" id="query-using-the-definition">按业务口径查询</Heading>

对于“按地区统计收入”，应用这些定义的查询可以写成：

```sql
SELECT
  region,
  CAST(SUM(
    CASE WHEN status IN ('paid', 'refunded')
      THEN amount - COALESCE(refund_amount, 0)
      ELSE 0
    END
  ) AS DOUBLE) AS net_revenue
FROM data
GROUP BY region
ORDER BY region;
```

上面六笔订单的结果为：

| region | net_revenue（美元） |
| --- | --- |
| East | 150 |
| West | 60 |

这只是一个示例查询。模型生成的 SQL 写法和列别名可能不同。

<Heading as="h2" id="check-and-maintain-your-definition">验证并维护定义</Heading>

与数据负责人确认行粒度、单位、记录范围、空值处理和时间归属。用可独立核对的结果验证生成的查询，覆盖退款、被排除的记录和连接基数。

将完整模型与数据源契约一起管理版本。AVA 使用固定版本的 Ossie JSON Schema 校验模型，并检查数据集、字段、键和关系的引用。上游参考校验器还检查表达式语法、指标作用域和可移植性。[Ossie 参考校验器](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/validation/validate.py)

字段定义、旧版 AVA 迁移方式和 SDK 签名见 [API 参考](/documentation/reference/api/#semantic-fields)。

<Heading as="h2" id="gravitino">从 Apache Gravitino 接入</Heading>

用 Gravitino 管理共享语义定义的所有者、权限和发布修订。AVA 消费已发布的 Ossie 快照，并通过配置好的引擎连接实际数据。语义模型标识为 `metalake/catalog/schema/model`，导出时另外指定修订号。Gravitino 在保存时按写入者的权限解析数据集指向的表或视图。执行查询时，以查询身份再次检查数据访问与来源映射。[Gravitino 源校验实现](https://github.com/apache/gravitino/blob/ac461b995d2e02aab4f542b686b633faa67fbd7a/server/src/main/java/org/apache/gravitino/server/web/rest/SemanticModelSourceValidator.java)

1. **固定已发布修订。** 在支持修订的 Gravitino 版本中，先用 `GET …/semantic-models/{model}/revisions` 选择已发布修订，再请求 `GET …/semantic-models/{model}/revisions/{revision}/ossie?format=json`。消费账号只需模型读取权限及必要的目录、模式访问权限。早期支持 Ossie 导出的版本可用 `…/semantic-models/{model}/ossie?format=json`，将审核后的导出快照连同摘要归档。[Gravitino 导出实现](https://github.com/apache/gravitino/blob/ac461b995d2e02aab4f542b686b633faa67fbd7a/server/src/main/java/org/apache/gravitino/server/web/rest/SemanticModelOperations.java)
2. **在导入前转换版本。** 所核对的 Gravitino 主线默认导出 `0.2.0.dev0`。导出对象已经是单模型扁平结构。保留 `datasets`、关系、根级指标以及 `expression.dialects`。把各级 `custom_extensions` 转为 `nonportable_extensions`，将 `data` 的 JSON 字符串解析成对象。显式核对键与关联列是否引用已声明的逻辑字段。转换后标记为 `0.3.0.dev0`，用该版本的官方参考校验器验证。只有确认属于 `OSSIE_SQL_2026` 的表达式才写入 `expression.sql`。[Gravitino 导出字段](https://github.com/apache/gravitino/blob/ac461b995d2e02aab4f542b686b633faa67fbd7a/common/src/main/java/org/apache/gravitino/semantic/OssieDocumentConverter.java) · [Ossie 核心规范](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/core-spec/spec.md)
3. **绑定来源并核对结果。** 例如，模型的逻辑数据集 `orders` 可指向 `sales.mart.orders`。先确认该来源在 AVA 当前引擎中可解析，再加载转换后的模型。若目录别名或表名不同，在部署时配置明确映射，并复核指标、连接粒度和典型结果。模型修订号和文件摘要随运行记录保存，方便复现。

```sh
ava schema "$DATASET_ID"
ava semantic "$DATASET_ID" --file sales.ossie.v0.3.json
```
