## Listen to events

AVA emits events while loading data, analyzing questions, and performing other operations. Subscribe by event name, or use `'*'` for every event:

```typescript
import { AVA } from '@antv/ava';

const ava = new AVA({ llm: { model: 'your-model' } });
const listener = (event) => console.log(event.type, event.data);

ava.on('*', listener);
try {
  await ava.source({ type: 'json', options: { data: [{ sales: 120 }] } });
} finally {
  ava.off('*', listener);
  await ava.dispose();
}
```

Each event has a lowercase `type` and a `data` object. For example, `sourcestart` has `data: { type: 'json' }`. Event classes and constants are not exported by the public package; use the names below as strings.

Most operations emit a start and an end event. A failed operation emits an end event with `data.error: { message, name? }` and rejects its Promise. Check for `error` before treating an end event as a success. A precondition failure, such as a missing source, can occur before the start event.

## Lifecycle events

These events mark AVA operations. Successful end events have empty data (`{}`).

| Operation | Start event | Start data | End event |
| --- | --- | --- | --- |
| Create or dispose an engine | `createstart` / `disposestart` | `{}` | `createend` / `disposeend` |
| Load a source | `sourcestart` | `{ type }` | `sourceend` |
| Discover or set schema | `schemastart` | `{}` | `schemaend` |
| Compute or set profile | `profilestart` | `{}` | `profileend` |
| Set semantic definitions | `semanticstart` | `{}` | `semanticend` |
| Analyze a question | `analyzestart` | `{ query }` | `analyzeend` |
| Visualize a result | `visualizestart` | `{ query }` | `visualizeend` |
| Suggest questions | `suggeststart` | `{}` | `suggestend` |

Cached schema reads and semantic reads do not emit events. `recommend()` and `viz()` do not emit their own events.

## Analysis events

These events describe steps within analysis. Direct calls to `translate()` and `query()` emit the same translation and query events.

| Step | Start event and data | End event and successful data |
| --- | --- | --- |
| Translate a question | `translatestart`: `{ query }`; direct analysis also includes `attempt` | `translateend`: `{ dsl, usage? }` |
| Execute a query | `querystart`: `{ dsl }` | `queryend`: `ExecutionResult` |
| Summarize results | `summarizestart`: `{ queryId }` | `summarizeend`: `{ queryExplanation, conclusion, limitations?, nextStep?, usage? }` |
| Direct analysis step | `stepstart`: `{ step: 0 }` | `stepend`: `{ step: 0, action: 'SQL', text }` |
| Loop iteration | `stepstart`: `{ step, finalAttempt? }` | `stepend`: `{ step, action, text, usage?, finalAttempt? }` |

`step` is zero-based. Direct analysis has one step covering translation, execution retries, and optional summarization. Loop analysis has one step per model response; its `action` is `EXPLORE`, `REFINE`, `SQL`, or `CONFIRM`, and `text` excludes that leading tag. The final fallback sets `finalAttempt: true` on both step events. See [analysis strategies](/documentation/analysis/strategies/).

A failed operation carries `data.error`. Failed step events also include `step`, any reported loop usage, and `finalAttempt` when applicable. A query error can be corrected by a later attempt; it does not necessarily mean the analysis failed. An error on `analyzeend` means the analysis stopped.

A successful direct analysis normally emits:

```text
analyzestart → stepstart → translatestart → translateend → querystart → queryend
             → summarizestart → summarizeend → stepend → analyzeend
```

Retries repeat translation and query events. With `includeSummary: false`, summary events are omitted and the returned `text` is empty. Structured summary fields such as `queryExplanation` and `limitations` are available on `summarizeend`. Both the returned analysis `text` and direct `stepend.data.text` contain only `conclusion`, or an empty string when summarization is disabled.

## Token usage

Read `event.data.usage` to observe model token counts:

| Operation | Event carrying usage |
| --- | --- |
| Direct analysis or standalone `translate()` | `translateend` for each translation attempt. |
| Direct analysis summary | `summarizeend`. |
| Loop analysis | `stepend` for each model response, including the final fallback. |

```typescript
ava.on('*', (event) => {
  if (event.data.usage) console.log(event.type, event.data.usage);
});
```

`usage` follows AI SDK's `LanguageModelUsage`, including `inputTokens`, `outputTokens`, and `totalTokens`. Counts can be undefined when the provider does not report them. Loop steps retain reported usage if response parsing or later execution fails; a model call that fails without returning usage cannot report it.

These events do not cover suggestions, chart generation, or text extraction. Treat them as analysis diagnostics, not a complete billing total.

## Relate events to steps

Analysis step, translation, query, and summary events emitted by `analyze()` include a `context` object:

| Field | Meaning |
| --- | --- |
| `eventId` | Unique ID formatted as `<pairId>:start` or `<pairId>:end`. Each operation and retry gets a new pair ID. |
| `stepId` | Groups a step and its operations. Step events use this ID as their pair ID. |
| `parentStepIds` | Empty in direct analysis and the first loop step; later loop steps contain the previous step's ID. |

The summary's `data.queryId` references the successful `queryend` event's full ID, including `:end`. Standalone `translate()` and `query()` calls do not include these context fields or emit step events.

## Listener parameters

| Method | Behavior |
| --- | --- |
| `on(name, listener, once?)` | Subscribe; the optional `once` flag defaults to `false`. |
| `once(name, listener)` | Subscribe for one invocation. |
| `off(name?, listener?)` | Remove a listener, all listeners for a name, or all listeners if omitted. Pass the same listener reference used to subscribe. |
| `emit(name, ...args)` | Emit an event manually. |
| `getEvents()` | Return the listener registry. |

These methods are synchronous; `on`, `once`, and `off` return the emitter. Synchronous listener errors propagate, and asynchronous listeners are not awaited. Event data is not copied; use `structuredClone(event)` if you need a snapshot.
