## Initialization

### Constructor

`new AVA(config: AVAConfig)`

| Parameter       | Type           | Required | Default / behavior                                            |
| --------------- | -------------- | -------- | ------------------------------------------------------------- |
| `config`        | `AVAConfig`    | Yes      | Configuration object.                                         |
| `config.llm`    | `LLMConfig`    | Yes      | [Model fields below](#model-options).                         |
| `config.engine` | `EngineConfig` | No       | `{ type: 'duckdb' }`; [engine fields below](#engine-options). |

The constructor does not load data. Engine creation happens on `source()`.

#### Model options

Fields below belong to `config.llm`.

| Field          | Type                                  | Required | Meaning / default                                                                 |
| -------------- | ------------------------------------- | -------- | --------------------------------------------------------------------------------- |
| `provider`     | `'openai' \| 'gateway'`               | No       | Defaults to OpenAI-compatible Chat Completions. Gateway reads AI_GATEWAY_API_KEY. |
| `model`        | `string \| LanguageModel`             | Yes      | Model name or a preconfigured AI SDK model instance.                              |
| `apiKey`       | `string`                              | No       | API key for the LLM provider                                                      |
| `baseURL`      | `string`                              | No       | Optional API base URL                                                             |
| `maxRetries`   | `number`                              | No       | Maximum retries for retryable model API failures. Default 3.                      |

String model names use OpenAI-compatible **Chat Completions** by default. A supplied model object is used directly. Usage callbacks are not a complete accounting stream for every LLM request.

#### Engine options

`config.engine.type` is required when `engine` is supplied. Supported values are `duckdb`, `python`, `javascript`, `supabase`, `clickhouse`, `sqlserver`, and `snowflake`, plus names registered through `registerEngine()`. Omitting `engine` selects DuckDB. JavaScript, Supabase, ClickHouse, SQL Server, and Snowflake accept no additional engine fields; connection credentials belong to `source()`.

##### DuckDB

Set `engine.type` to `duckdb`. These are all additional fields accepted on `engine`.

| Field                      | Type      | Required | Meaning / default                                                               |
| -------------------------- | --------- | -------- | ------------------------------------------------------------------------------- |
| `memoryLimit`              | `string`  | No       | Memory limit, e.g. '512MB'. Default '512MB'.                                    |
| `threads`                  | `number`  | No       | Number of worker threads. Default 1.                                            |
| `maxTempDirectorySize`     | `string`  | No       | Max size of the spill (temp) directory, e.g. '1GB'. Unset = unlimited.          |
| `queryTimeoutMs`           | `number`  | No       | Per-query timeout in milliseconds. Default 30000.                               |
| `allowCommunityExtensions` | `boolean` | No       | Allow DuckDB community extensions during source loading when explicitly needed. |

##### Python

Set `engine.type` to `python`. These are all additional fields accepted on `engine`.

| Field            | Type                                         | Required | Meaning / default                                                                                                                                                                                                                                                                         |
| ---------------- | -------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `execute`        | `(code: string) => Promise<ExecutionResult>` | No       | Override local python3 execution with a custom environment. Local execution is not sandboxed. Run the complete Python script and return its JSON output as ExecutionResult. Each query first sends a compile-only validation script, then the data execution script with source loading and result limits. Configure remote execution deadlines separately. |
| `queryTimeoutMs` | `number`                                     | No       | Wait and local process deadline for each validation or execution call. Default 30000 ms.                                                                                                                                                                                                                 |

##### Registered engines

Set `engine.type` to the name passed to `registerEngine()`. Additional fields are forwarded to the engine constructor as `options`. This is an SDK-only capability; the CLI supports built-in engine names.

| Field        | Type            | Required          | Meaning / default                          |
| ------------ | --------------- | ----------------- | ------------------------------------------ |
| `type`       | `string`        | Yes               | Registered engine name, such as `'sales'`. |
| Other fields | Engine-specific | Depends on engine | Validated by the registered engine.        |

## Data

### source

```typescript
source(configs: DataSourceConfig | DataSourceConfig[]): Promise<void>
```

Loads data sources through the configured engine. Schema discovery starts when an operation needs it.

```typescript
await ava.source({ type: 'json', options: { data: [{ revenue: 120 }] } });
```

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `configs` | `DataSourceConfig \| DataSourceConfig[]` | Yes | A [source configuration](/documentation/data/sources/#connect-a-source) or a nonempty array of configurations. |

In the Node.js SDK, DuckDB can load multiple sources in one call. See [Connect multiple sources](/documentation/data/sources/#connect-multiple-sources) for batch configuration and naming.

Each call releases the active engine and clears the saved schema, profile, and semantic definitions before loading. A failed load leaves the instance without an active dataset. Await pending operations before calling `source()`.

### schema

```typescript
schema(options?: SchemaOptions, setter?: (options: SchemaOptions) => Schema): Promise<Schema>
```

Returns the structure of the loaded source. Without a setter, AVA returns the saved schema or discovers it through the engine and saves it.

```typescript
const schema = await ava.schema();
```

To supply an existing schema, pass a function that returns it:

```typescript
await ava.schema(undefined, () => savedSchema);
```

| Parameter | Type | Required | Meaning / default |
| --- | --- | --- | --- |
| `options` | `SchemaOptions` | No | `{}`; currently has no configurable fields. |
| `setter` | `(options: SchemaOptions) => Schema` | No | Returns the schema to save instead of discovering it through the engine. |

A setter receives the options object (default `{}`) and returns a `Schema` synchronously. Its result replaces the saved schema and clears the saved profile. AVA validates and copies the result; invalid results or thrown errors reject the call without changing previous metadata.

Requires a loaded source. Analysis and profiling obtain the schema when needed; direct `query()` does not. For the walkthrough, see [Inspect your data](/documentation/data/schema/).

#### Schema structure

| Field | Meaning |
| --- | --- |
| `models` | Tables or views available for queries; required. |
| `models[].name` | Model name. |
| `models[].tableReference` | Physical source identity: `table`, with optional `catalog` and `schema`. |
| `models[].columns` | Columns, each with `name`, `type`, and optional `notNull`. |
| `models[].primaryKey` | One column name, or a nonempty ordered array for a composite key. |
| `models[].uniqueKeys` | Array of alternative keys; each entry is a column name or a composite-key array. |
| `relationships` | Discovered foreign-key relationships, when available. |
| `views` | Named view queries with `name` and `statement`, when available. |

The details depend on the source and engine. A query result's `schema` describes its output columns and is not a source `Schema`.

### profile

```typescript
profile(options?: ProfileOptions, setter?: (options: ProfileOptions) => Profile): Promise<Profile>
```

Calculates and saves statistics for the loaded source through the engine. Each call without a setter computes a fresh profile and requires engine profiling support.

```typescript
const profile = await ava.profile({ metrics: ['row_count', 'mean'] });
```

To supply an existing profile, pass a function that returns it:

```typescript
await ava.profile(undefined, () => savedProfile);
```

| Parameter | Type | Required | Meaning / default |
| --- | --- | --- | --- |
| `options` | `ProfileOptions` | No | `{}`; uses the default metrics below. |
| `options.metrics` | `MetricConfig[]` | No | Metrics for engine computation. A supplied list replaces the defaults. |
| `setter` | `(options: ProfileOptions) => Profile` | No | Returns the profile to save instead of computing it through the engine. |

A setter receives the options object (default `{}`) and returns a `Profile` synchronously. It does not require engine profiling support. AVA validates and copies its result; invalid results or thrown errors reject the call without changing previous metadata. The options are passed to the setter; AVA does not calculate or filter metrics on its behalf.

Requires a loaded source. Both paths replace the saved profile, which analysis, translation, and suggestions can reuse. Setting a profile does not replace the saved schema.

#### Profile format

A profile attaches observations to existing schema models and columns by name:

| Field | Meaning |
| --- | --- |
| `models[].name` | Model to enrich. |
| `models[].metrics` | Table statistics such as `row_count`. |
| `models[].columns[].name` | Column to enrich within that model. |
| `models[].columns[].metrics` | Column statistics such as `mean`. |
| `models[].columns[].properties.logicalType` | Normalized category: `numeric`, `string`, `boolean`, `date`, or `unknown`. |

A missing metric means it was not computed, not zero. Setting a schema clears the saved profile, so supply the schema first when providing both manually. Loading another source or calling `dispose()` clears schema, profile, and semantic definitions. Updating schema or profile retains semantic definitions.

#### Metrics

The default metrics are `row_count`, `null_count`, `distinct_count`, `top_values`, `min`, `max`, and `mean`. Additional built-in metrics are `duplicate_count`, `min_length`, `max_length`, `sum`, `stddev`, and `median`.

Each entry is a metric name or an object with an `id` and metric-specific options:

```typescript
await ava.profile({
  metrics: ['row_count', { id: 'top_values', limit: 5 }],
});
```

| Field | Type | Default / behavior |
| --- | --- | --- |
| `id` | `string` | Required for object entries; the metric name. |
| `limit` | `number` | `top_values` only. Default `3`; a non-negative safe integer. |
| `maxDistinctRatio` | `number` | `top_values` only. Default `0.5`; a finite number from `0` to `1`. |

Other built-in metrics accept no additional options. Unknown metrics and unknown option names are rejected when the engine computes the profile. Availability depends on the engine and field type.

`metrics: []` produces empty metric objects. A new profile replaces previous statistics; metrics are not accumulated.

### semantic

```typescript
semantic(options?: SemanticOptions, setter?: (options: SemanticOptions) => Semantic | null): Promise<Semantic | null>
parseSemantic(text: string): Semantic
```

`semantic()` returns a copy of the current Apache Ossie model or `null` when empty. After loading a source, pass a setter to replace the complete model, or return `null` to clear it. The setter receives an empty options object. If validation or the setter fails, the current model stays active.

`parseSemantic()` validates a YAML or JSON document and returns a model. The object contract is available as `semanticOutputSchema`. Both work without a loaded data source or model credentials.

```typescript
await ava.semantic(undefined, () => ({
  version: '0.3.0.dev0',
  name: 'sales_reporting',
  datasets: [{
    name: 'orders',
    source: 'data',
    metrics: [{ name: 'total_revenue', expression: { sql: 'SUM(source.revenue)' } }],
  }],
}));
const model = await ava.semantic();
await ava.semantic(undefined, () => null);
```

`analyze()`, `translate()`, and `suggest()` receive the model as `DataModel.semantic` alongside the physical schema and statistical profile. AVA preserves vendor extensions in the stored document. Reloading or disposing of a source clears its model.

See the [sales example](/documentation/data/semantic/) and the [Ossie model reference](#semantic-fields).

## Analysis and queries

### analyze

`analyze(query: string, config?: AnalysisConfig): Promise<AnalysisResponse>`

| Parameter                    | Type                               | Required                  | Default / behavior                                                                                                              |
| ---------------------------- | ---------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `query`                      | `string`                           | Yes                       | Natural-language question.                                                                                                      |
| `config`                     | `AnalysisConfig`                   | No                        | `{}`.                                                                                                                           |
| `config.includeSummary`      | `boolean`                          | No                        | `true`; `false` returns empty `text`.                                                                                           |
| `config.maxRows`             | `number`                           | No                        | `200`; see [execution limits](#executionoptions).                                                                               |
| `config.maxResultBytes`      | `number`                           | No                        | `1048576`; see [execution limits](#executionoptions).                                                                           |
| `config.strategy`            | `AnalysisStrategyConfig`           | No                        | Direct analysis.                                                                                                                |
| `config.strategy.type`       | `'direct'` / `'loop'` | When strategy is provided | Selects the strategy.                                                                                                           |
| `config.strategy.maxRetries` | `number`                           | No; `direct` only         | `2` with explicit `type: 'direct'`; currently `10` when the strategy is omitted. Correction attempts after the first execution. |
| `config.strategy.maxSteps`   | `number`                           | No; `loop` only           | `12`; maximum reasoning steps.                                                                                                  |

These retry controls differ from `llm.maxRetries`. See [strategy behavior and requirements](/documentation/analysis/strategies/).

Requires a loaded source. Returns an [ExecutionResult](#executionresult) plus:

| Result field | Type     | Presence | Meaning                                                                   |
| ------------ | -------- | -------- | ------------------------------------------------------------------------- |
| `query`      | `string` | Always   | Original question.                                                        |
| `text`       | `string` | Always   | Summary, or empty when disabled.                                          |
| `markdown`   | `string` | Optional | Markdown content.                                                         |
| `sql`        | `string` | Optional | Executed query or DSL; the property name is retained for non-SQL engines. |

### translate

`translate(query: string): Promise<string>`

| Parameter | Type     | Required | Meaning                    |
| --------- | -------- | -------- | -------------------------- |
| `query`   | `string` | Yes      | Natural-language question. |

Requires a loaded source. Returns generated DSL without executing it; use `query()` to execute that string.

### query

`query(dsl: string, options?: ExecutionOptions): Promise<ExecutionResult>`

| Parameter                | Type               | Required | Default / behavior                                      |
| ------------------------ | ------------------ | -------- | ------------------------------------------------------- |
| `dsl`                    | `string`           | Yes      | Executable statement in the selected engine's language. |
| `options`                | `ExecutionOptions` | No       | Default execution limits below.                         |
| `options.maxRows`        | `number`           | No       | `200`.                                                  |
| `options.maxResultBytes` | `number`           | No       | `1048576` bytes.                                        |

Requires a loaded source. Does not generate or summarize a query with the model.

#### ExecutionOptions

| Field            | Type     | Default           | Accepted values / behavior                                                                                       |
| ---------------- | -------- | ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `maxRows`        | `number` | `200`             | Rounded down and bounded to `1`–`1000000`; values outside the safe integer range after rounding use the default. |
| `maxResultBytes` | `number` | `1048576` (1 MiB) | Finite values are rounded down and clamped to at least `1`; non-finite values use the default.                   |

These limits bound returned data; they are separate from engine execution timeouts.

#### ExecutionResult

| Field           | Type                             | Presence       | Meaning                                                 |
| --------------- | -------------------------------- | -------------- | ------------------------------------------------------- |
| `schema`        | `QueryColumn[]`                  | Always         | Returned column metadata.                               |
| `schema[].name` | `string`                         | Always         | Column name.                                            |
| `schema[].type` | `string`                         | Optional       | Native type name, if available.                         |
| `data`          | `T[]`                            | Always         | Returned rows.                                          |
| `truncated`     | `true`                           | When truncated | Result was bounded.                                     |
| `truncatedBy`   | `'maxRows'` / `'maxResultBytes'` | When truncated | Limit that stopped the result.                          |
| `rowCount`      | `number`                         | When known     | Row count when execution reaches the end of the result. |

### suggest

`suggest(count?: number): Promise<SuggestResult[]>`

| Parameter | Type     | Required | Default / behavior                  |
| --------- | -------- | -------- | ----------------------------------- |
| `count`   | `number` | No       | `3`; requested number of questions. |

Requires a loaded source. Returns suggestions sorted by descending score, each with `query: string`, `score: number` (0–1), and `reason: string`.

## Visualization

### visualize and recommend

`visualize(analysisResult: Pick<AnalysisResponse, 'query' | 'data'>): Promise<VisualizeResponse | null>`

`recommend(analysisResult: Pick<AnalysisResponse, 'query' | 'data'>): Promise<ChartSpec | null>`

Both methods accept the same input:

| Parameter              | Type                                        | Required | Meaning                                                          |
| ---------------------- | ------------------------------------------- | -------- | ---------------------------------------------------------------- |
| `analysisResult`       | `Pick<AnalysisResponse, 'query' \| 'data'>` | Yes      | An analysis result or an object containing the two fields below. |
| `analysisResult.query` | `string`                                    | Yes      | Question or visualization intent.                                |
| `analysisResult.data`  | `AnalysisResponse['data']`                 | Yes      | Rows to visualize.                                               |

Neither requires a loaded source. Both use the model and return `null` for empty data or when no chart is recommended. Generation errors propagate. `recommend()` returns a `ChartSpec`; `visualize()` additionally returns `html: string` containing a standalone chart page.

### viz

`viz(spec: ChartSpecInput): Promise<string>`

| Parameter        | Type        | Required | Meaning                                                                                             |
| ---------------- | ----------- | -------- | --------------------------------------------------------------------------------------------------- |
| `spec`           | `ChartSpecInput` | Yes      | Chart specification before defaults are applied. |
| `spec.chartType` | `ChartType` | Yes      | One of the types below; must match `config.type` for JSON charts. |
| `spec.config`    | `ChartSpecInput['config']` | Yes    | Native GPT-Vis config; a missing `config.type` is filled from `chartType`. For `summary`, pass a GPT-Vis summary string. |

`ChartType` values: `line`, `column`, `bar`, `pie`, `area`, `scatter`, `dual-axes`, `histogram`, `boxplot`, `radar`, `funnel`, `waterfall`, `liquid`, `word-cloud`, `violin`, `venn`, `treemap`, `sankey`, `table`, `summary`.

GPT-Vis supports 26 visualization types. AVA can recommend the 20 types above. For `summary`, `config` contains the native GPT-Vis summary string. You can also render a summary directly through `viz({ chartType: 'summary', config: '# Sales report' })`. The six relationship graph types are outside AVA's current contract. `ChartSpec` describes the normalized result, with `config.type` filled for JSON charts.

`spec.html?: string` accepts the complete result from `visualize()`. Rendering always uses `config` to generate fresh HTML; an existing `html` value is not reused. Other unknown envelope fields are rejected.

Returns a standalone HTML string. Does not require a loaded source or call a model. See [chart specifications](/documentation/visualization/overview/#recommend).

## Runtime contracts

AVA pins `@antv/gpt-vis` to 1.3.1. The generated HTML loads that exact version from the CDN; its types also check the native chart contracts. Category, name and group labels follow the native string types; time labels can also be numbers. Treemap nodes require `value`. Chart themes accept built-in names and native theme objects, and native options include subtitles, waterfall intermediate totals and Venn string sets.

The Node and browser entry points export shared runtime schemas. SDK `source()`, `recommend()`, `viz()` and the CLI use these contracts at their input boundaries.

MCP and other integrations import API schemas and data types from the SDK entry point. Use `@antv/ava` in Node and `@antv/ava/browser` in browser code:

```typescript
import { queryInputSchema, queryOutputSchema } from '@antv/ava';
import type { ExecutionResult } from '@antv/ava';

const input = queryInputSchema.parse({ dsl: 'SELECT * FROM data', options: { maxRows: 10 } });
const output: ExecutionResult<unknown> = queryOutputSchema.parse(await ava.query(input.dsl, input.options));
```

API types are derived with `z.input<typeof inputSchema>` and `z.output<typeof outputSchema>`, so runtime validation and TypeScript share one field definition, including structure, profile, semantic, analysis and suggestions. Source types describe input before normalization (for example, Excel's `header` remains optional). `ExecutionResult<Row>` preserves your query's row type; runtime validation checks the result envelope, not the caller's generic row fields. ClickHouse options retain the official client's native types, including TLS buffers, agents and callbacks; those native options pass through to the client.

Public schemas follow API input/output names. Multi-argument methods use named argument objects; single-argument methods use the argument directly. Omitted options still use SDK defaults. Setter callbacks remain SDK functions and are excluded from the data schemas; metadata passed to setters can be validated with the corresponding output schema. CLI session fields and stricter transport limits belong to the adapter.

| API | Input schema and shape | Output schema |
| --- | --- | --- |
| `source` | `sourceInputSchema`: source config | No result (`void`) |
| `schema` | `schemaInputSchema`: options `{}` | `schemaOutputSchema` |
| `profile` | `profileInputSchema`: `{ metrics? }` | `profileOutputSchema` |
| `semantic` | `semanticInputSchema`: options `{}` | `semanticOutputSchema` |
| `query` | `queryInputSchema`: `{ dsl, options? }` | `queryOutputSchema` |
| `analyze` | `analyzeInputSchema`: `{ query, config? }` | `analyzeOutputSchema` |
| `translate` | `translateInputSchema`: question string | `translateOutputSchema`: DSL string |
| `suggest` | `suggestInputSchema`: count | `suggestOutputSchema`: suggestion array |
| `recommend` | `recommendInputSchema`: `{ query, data }` | `recommendOutputSchema`: chart spec or `null` |
| `visualize` | `visualizeInputSchema`: `{ query, data }` | `visualizeOutputSchema`: chart spec with required HTML, or `null` |
| `viz` | `vizInputSchema`: chart spec before defaults | `vizOutputSchema`: HTML string |

The Node and browser entry points export the same API input/output schemas. Type names remain unchanged, including `DataSourceConfig`, `SchemaOptions`, `ExecutionResult` and `AnalysisResponse`. `ExecutionResult<Row>` and `AnalysisResponse<Row>` retain row generics and default to object rows. `dispose()` has neither input data nor a return value, so it needs no data schema.

For MCP or other JSON Schema tools, use `z.toJSONSchema(inputSchema, { io: 'input' })` for inputs and `z.toJSONSchema(outputSchema, { io: 'output' })` for outputs. Input mode describes values before normalization; output mode includes required normalized fields such as chart `config.type`.

## Cleanup

### dispose

`dispose(): Promise<void>` takes no parameters. Releases the current engine and clears the schema, profile, and semantic definitions. Await it in a `finally` block.

## Semantic model reference

### Semantic fields

`Semantic` follows the pinned Apache Ossie core specification `0.3.0.dev0`. Each document has one top-level `name` and at least one dataset. [Official core specification](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/core-spec/spec.md), [JSON Schema](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/core-spec/ossie-schema.json)

| Field | Purpose |
| --- | --- |
| `datasets[].source` | Physical table, view or query that supplies rows. |
| `datasets[].fields` | Named row-level expressions. Keys and relationship column lists refer to these names. |
| `datasets[].metrics` | Calculations scoped to that dataset. Use `source.column` to reference a physical source column. |
| Top-level `metrics` | Calculations scoped to the whole model. Qualify dataset fields as `dataset.field`. |
| `relationships` | Paired join fields between datasets, from the many side to the one side. |
| `ai_context` | Business usage, synonyms and examples for the model or an entity. |
| `nonportable_extensions` | Vendor-tagged JSON metadata preserved on readback. |

Provide `expression.sql` in `OSSIE_SQL_2026`, dialect alternatives in `expression.dialects`, or both. The top-level SQL form is authoritative for `OSSIE_SQL_2026`.

### Migrate a legacy AVA definition

Map each former `model` or SQL-backed view to a `dataset` with a physical table or query as its `source`. Move columns and cube dimensions into `fields`, and cube measures into dataset or model `metrics` according to scope. Convert primary and unique keys to lists of declared fields. Translate equality joins into paired `from_columns` and `to_columns`. Keep business rules that have no direct core field, such as drill-down order, in `ai_context`. Use vendor extensions for proprietary metadata. Review arbitrary join conditions and derived sources before importing them.

If your earlier OSI file wraps its model in `semantic_model`, follow the upstream migration guidance to produce a flat model document. [Ossie migration instructions](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/core-spec/spec.md#migrating-earlier-document-shapes)

### Semantic validation

AVA checks the published document structure and the model's declared names, keys and relationship references. Run the upstream reference validator for expression syntax, metric scoping and portability diagnostics. Check source mappings and metric results against your data. [Ossie reference validator](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/validation/validate.py)
