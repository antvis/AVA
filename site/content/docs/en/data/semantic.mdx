Suppose a user asks: **“Show revenue by region.”** Here is the order table behind that question, also used in [Inspect your data](/documentation/data/schema/):

| order_id | region | status | amount | refund_amount | ordered_at |
| --- | --- | --- | --- | --- | --- |
| 1 | East | paid | 120 | 20 | 2026-01-03 |
| 2 | East | refunded | 80 | 80 | 2026-01-04 |
| 3 | East | pending | 200 | 0 | 2026-01-05 |
| 4 | West | paid | 90 | 30 | 2026-01-06 |
| 5 | East | paid | 50 | `null` | 2026-01-07 |
| 6 | West | cancelled | 500 | 0 | 2026-01-08 |

The structure tells AVA that `amount` and `refund_amount` are numbers. It does not tell AVA which orders count as revenue. You supply that meaning through `semantic()`.

## Decide what revenue means

For this example, agree on three rules:

- Count `paid` and `refunded` orders; exclude `pending` and `cancelled` orders.
- Subtract cumulative refunds from the original amount. A missing refund is zero. Amounts are USD.
- Group by the order's region and use its original order date.

Apply those rules to the rows above:

| Order | Contribution to revenue | Why |
| --- | --- | --- |
| 1 | 100 USD | 120 minus the 20 refund. |
| 2 | 0 USD | Fully refunded: 80 minus 80. |
| 3 | 0 USD | Pending, so excluded. |
| 4 | 60 USD | 90 minus the 30 refund. |
| 5 | 50 USD | The missing refund is treated as zero. |
| 6 | 0 USD | Cancelled, so excluded. |

East therefore has **150 USD** in revenue; West has **60 USD** . The definition below records the rules that produce those numbers.

## Write the definition

Save the model as `sales.ossie.yaml`. It maps the logical dataset `orders` to the table `data`. `fields` exposes the grouping fields and `metrics` records the calculation. In a dataset-scoped metric, `source.amount` refers directly to a column of that dataset's source.

```yaml
version: 0.3.0.dev0
name: sales_reporting
description: Orders and their cumulative refunds, in USD.
datasets:
  - name: orders
    source: data
    primary_key: [order_id]
    fields:
      - name: order_id
        expression: { sql: order_id }
        datatype: Integer
      - name: region
        expression: { sql: region }
        datatype: String
      - name: order_date
        expression: { sql: "CAST(ordered_at AS DATE)" }
        datatype: Date
        dimension: { is_time: true }
    metrics:
      - name: net_revenue
        description: Revenue after refunds, in USD.
        datatype: Decimal
        expression:
          sql: >-
            SUM(CASE WHEN source.status IN ('paid', 'refunded')
              THEN source.amount - COALESCE(source.refund_amount, 0)
              ELSE 0 END)
```

## Load the model

Load the source first, then import the model. The CLI accepts a YAML or JSON file or reads one from stdin with `--file -`.

```sh
ava semantic "$DATASET_ID" --file sales.ossie.yaml
ava semantic "$DATASET_ID" > sales.ossie.json
ava semantic "$DATASET_ID" --clear
```

The SDK accepts the same document as an object. Use `parseSemantic` to read its YAML or JSON representation.

```typescript
import { readFile } from 'node:fs/promises';
import { parseSemantic } from '@antv/ava';

const model = parseSemantic(await readFile('sales.ossie.yaml', 'utf8'));
await ava.semantic(undefined, () => model);
const saved = await ava.semantic();
```

Each import replaces the session model. A new source or `dispose()` clears it. Updates to schema and profile retain the model. `analyze()`, `translate()`, and `suggest()` consume the model alongside physical metadata. For `query()`, apply the definitions in the statements you submit.

### Query using the definition

For “Show revenue by region,” a query applying these definitions can look like this:

```sql
SELECT
  region,
  CAST(SUM(
    CASE WHEN status IN ('paid', 'refunded')
      THEN amount - COALESCE(refund_amount, 0)
      ELSE 0
    END
  ) AS DOUBLE) AS net_revenue
FROM data
GROUP BY region
ORDER BY region;
```

The result for the six orders above is:

| region | net_revenue (USD) |
| --- | --- |
| East | 150 |
| West | 60 |

This is an example query; model-generated SQL and column aliases can vary.

## Check and maintain your definition

Confirm grain, units, eligibility, null handling, and time attribution with the data owner. Compare generated queries against results you can verify, including refunds, excluded records, and join cardinality.

Keep the complete model in version control alongside its source contract. AVA validates against the pinned Ossie JSON Schema and checks declared dataset, field, key, and relationship references. The upstream validator also checks expression syntax, metric scoping, and portability. [Ossie reference validator](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/validation/validate.py)

For field definitions, migration from the old AVA format, and the SDK signature, see the [API reference](/documentation/reference/api/#semantic-fields).

## Import from Apache Gravitino

Use Gravitino to manage ownership, access and publication of shared models. AVA reads a published Ossie snapshot and connects to the data through its configured engine. A Gravitino model is identified by metalake, catalog, schema and model name. At write time, Gravitino resolves the source table or view using the author's permissions. Check the source mapping and data permissions again for the query identity. [Gravitino source validator](https://github.com/apache/gravitino/blob/ac461b995d2e02aab4f542b686b633faa67fbd7a/server/src/main/java/org/apache/gravitino/server/web/rest/SemanticModelSourceValidator.java)

1. **Pin a published revision.** On a deployment with revision support, select a published revision from `GET …/semantic-models/{model}/revisions` and fetch `GET …/semantic-models/{model}/revisions/{revision}/ossie?format=json`. Give the reader access to the model and its parent catalog and schema. If only the unversioned export is available, archive the reviewed export and its digest. [Gravitino export implementation](https://github.com/apache/gravitino/blob/ac461b995d2e02aab4f542b686b633faa67fbd7a/server/src/main/java/org/apache/gravitino/server/web/rest/SemanticModelOperations.java)
2. **Convert the protocol version before loading.** The Gravitino revision referenced here exports `0.2.0.dev0` by default as a flat single-model document. Keep datasets, relationships, root metrics and `expression.dialects`. Convert `custom_extensions` at every level to `nonportable_extensions` and decode each JSON string in `data` to an object. Check that keys and relationships refer to declared fields. Set the converted model's version to `0.3.0.dev0` and run the upstream validator. Set `expression.sql` only for verified `OSSIE_SQL_2026` expressions. [Gravitino export format](https://github.com/apache/gravitino/blob/ac461b995d2e02aab4f542b686b633faa67fbd7a/common/src/main/java/org/apache/gravitino/semantic/OssieDocumentConverter.java) · [Ossie core specification](https://github.com/apache/ossie/blob/aedf08651451306896d98e17657c16c99848ef78/core-spec/spec.md)
3. **Bind the source and check results.** For a logical dataset `orders` pointing to `sales.mart.orders`, ensure AVA's configured engine can resolve that table. Configure explicit mappings when deployed catalog or table names differ. Check metric values and join grain against known results, and retain the revision number and document digest with the run.
